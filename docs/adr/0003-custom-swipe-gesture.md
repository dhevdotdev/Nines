# Habit-row swipe actions use a hand-rolled AnchoredDraggableState, not M3's SwipeToDismissBox

Swipe-to-edit/archive on `HabitRow` is built directly on `androidx.compose.foundation.gestures.AnchoredDraggableState` with small (120dp) anchors and a custom `onDismiss`-equivalent effect, rather than `androidx.compose.material3.SwipeToDismissBox`.

**Why**: `SwipeToDismissBox` always anchors a dismissal at ± the row's full width. That caused two real, user-visible bugs in order: (1) the deprecated `confirmValueChange` API fires live as the drag crosses each anchor mid-drag, so an action could commit while still held, before release; (2) even after switching to the non-deprecated `settledValue`/`onDismiss` API (which is correctly release-gated) and visually clamping the rendered card to a smaller reveal distance, the real settle animation still had to travel the full (now invisible) row width before firing — a very noticeable release-to-action lag. Anchoring the real drag state at the small reveal distance we actually want fixes both: settling has almost nothing left to travel, and the action only ever fires post-release.

**Considered and rejected**: `SwipeToDismissBox` with `confirmValueChange` (fires mid-drag — rejected); `SwipeToDismissBox` with `onDismiss` + a purely visual offset clamp (correct gating, but laggy — rejected). Three total redesigns preceded this one, including an earlier abandoned attempt combining `sh.calvin.reorderable`'s drag handle directly on the same gesture surface as swipe-dismiss, which is why list reordering is now a separate, mutually-exclusive top-bar-toggled mode instead of a per-row always-on handle.
